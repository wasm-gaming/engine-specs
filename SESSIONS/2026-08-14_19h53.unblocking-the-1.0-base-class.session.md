# Unblocking the 1.0 base class

2026-08-14 · written from the pilot engine, [rsdkv4-wasm](https://github.com/wasm-gaming/rsdkv4-wasm)

`PLAN-1.0.md` §4 makes rsdkv4 the pilot: *"lo que aprenda ahí se corrige en el contrato **antes**
de tocar el segundo motor."* It has now learned something, and it has stopped — not because the
migration is hard, but because migrating today means writing the base class's job inside one
engine and deleting it later. This is what has to happen here for that to unblock, in the order
that costs least.

## Where this repo actually is

Verified in the working copy, not assumed:

| | state |
| --- | --- |
| **F1 · Layer A** | not started — `src/manifest.ts` still declares `mountPath` and no `contractVersion`; `schema/engine-manifest.schema.json` and `src/validate.ts` match it |
| **F2 · Layer B types** | **done**, shipped in `0.2.7` (`7aa8aed`) |
| **F3 · implementation** | not started — 35 `abstract` members and a constructor that says so |
| F4 · demo as reference engine | blocked on F3 |

One naming drift worth fixing while it is cheap: `PLAN-1.0.md` still calls F3 `EngineBuilder` and
the instance `EngineInstance`. The code that shipped calls them `EngineSDK` and `EnginePlay`. The
plan should follow the code, or the next reader will look for a class that does not exist.

## What the blockage actually is

The class is a shape with no body:

```ts
constructor(setup?: EngineSetup<Config, Options>) {
  void setup; // shape only: the base class does not run yet
}
```

Everything else is `abstract`. So `class Rsdkv4SDK extends EngineSDK` inherits **nothing
executable**, and the engine has to implement, by itself, every rule the contract states as
normative:

- the chain — every setter returns `this`;
- the freeze — `assets()`, `config()`, `storage()` and `mount()` throw with a live engine, while
  `options()` deliberately does **not**, because it describes the next session rather than the
  engine. That asymmetry is easy to implement backwards, and nothing would catch it;
- the cumulative payload — flat, one level, and `null` is an explicit value rather than "leave
  unchanged";
- `boot()` idempotent, `start()` = `boot().restart()`;
- handlers copied onto the play instance, `missingAssets()` — including the rule that a `{}` left
  by a lost JSON round-trip counts as absent, not present — and thunk resolution.

Twelve engines are meant to **inherit** that, not re-derive it. Written in the pilot, the
semantics get frozen by accident in one engine's source instead of in the shared class — which is
precisely what moving Layer B from interfaces to classes was for.

## A · The three type defects

First, because they change the shape F3 implements, and they are hours rather than days.

**1. Abstract optional members.** `EnginePlay` declares `saves?`, `deleteSave?`, `saveState?`,
`loadState?`, `screenshot?` (and `EngineSDK` declares `saves?`) as `abstract … ?()`. That is a
contradiction in terms: `?` says "you may not have this", `abstract` says "you are required to
provide it". An implementor gets the worst of both — TypeScript pushes them to write the member,
and the type gives a caller no way to know whether it is real. Presence is already declared by
`capabilities` in the manifest; the type should follow that, not duplicate it. Options worth
weighing: gate them on a capabilities type parameter, or drop `abstract` and give the base class
a default that throws `unsupported` (§9.2), so the manifest stays the single source of truth.

**2. Crossed generics.**

```ts
EngineSDK<Config, Options, Play>   // Config first
EnginePlay<Options, Config>        // Options first
```

The same two parameters in opposite order across the two classes any engine has to write
together. A transposition compiles cleanly and means the opposite. Align them.

**3. `payload: unknown` in the `start` event.** It should be `Partial<Options>`: the event carries
exactly what the caller passed, and `unknown` forces a cast in every host that listens.

## B · F3 · Implement the base class

The list above, implemented once, plus the piece that is the real deliverable of this phase: **the
conformance suite** — a test that takes an engine class and checks the normative rules against it,
which the twelve engines import into their own CI. Without it "conforms to the contract" stays an
opinion.

The single line the pilot is waiting to put in its CI:

```ts
import type { EngineSDKClass } from '@wasm-gaming/engine-specs';
const _contract: EngineSDKClass<Rsdkv4Config, Rsdkv4Options, Rsdkv4Play> = Rsdkv4SDK;
```

Verification: `tests/types.test-d.ts` (F2's compile test) still green, plus the suite passing
against the demo engine in F4. **The demo passing the conformance suite is the proof that 1.0 can
be implemented at all** — and it is worth doing before the pilot migrates, not after, because
whatever the demo cannot express, rsdkv4 will hit harder.

## C · F1 · Layer A at 1.0

`contractVersion`, `config` instead of `options`, no `mountPath` (the VFS becomes internal) and no

This one is independent of A and B and can go in parallel. It blocks rsdkv4's own phase 2: its

## What the pilot learned, and what this repo should do with it

The findings below come from running the engine for real, not from reading the spec. Full detail
in rsdkv4's session file, `SESSIONS/2026-08-14_12h35.sdk-migration-to-contract-1.0.session.md`.

**1. The asynchronous API is right, and now there are numbers.** The reason Layer B went async was
that the engine has to be able to live in a worker. It now does: RSDKv4 boots on a pthread, reads
its pack there and runs Green Hill Zone at a steady 60 fps. The cost in input latency, measured
over 40 keypresses per build:

| | min | p50 | p90 | mean |
| --- | --- | --- | --- | --- |
| main thread | 0.37 | 9.20 | 14.57 | **8.41 ms** |
| worker | 0.41 | 10.17 | 14.95 | **9.35 ms** |

About 1 ms, and the minimum says why: **the thread hop itself costs 0.04 ms**. What dominates both
columns is frame quantisation — a key that arrives just after the engine read its input waits for
the next tick — and the theoretical mean of that wait at 60 Hz is 8.3 ms, which is where both
land. The worker does not cost responsiveness.

**2. Keep every live-engine member asynchronous.** `EnginePlay` already returns `Promise` /
`PlayPromise` from everything that touches a running engine. Hold that line: rsdkv4 0.1 exposed
its engine bridges synchronously, and now that the engine runs on another thread those calls are a
genuine data race — the host calling `web_audio_stop()` from the main thread mutates state the
engine thread is mixing at that moment. The pilot is evidence *for* the async decision, and the
sync getters that survive in 0.1 are the bug.

**3. `mount()` must not assume an irreversible canvas transfer.** The rsdkv4 plan had assumed
that in a worker, `mount(canvasEl)` implies `transferControlToOffscreen()`, making "only before
`start()`" physics rather than convention. That turned out to be wrong for at least one real
engine: RSDKv4 renders in software and needs no WebGL at all, so its canvas stays on the main
thread and the transfer never happens. Worse, with SDL2 the transfer actively breaks the engine —
SDL asks EGL for a context, Emscripten's EGL is proxied to the main thread, and a transferred
canvas cannot hand out a context there. So the contract should keep `mount()` neutral about how
the picture reaches the page, and state the "before `start()`" rule as a rule, not as a
consequence of OffscreenCanvas.

**4. `capabilities.saves: 'storage'` is a real promise with a real cost.** For rsdkv4 it means
parsing `SData.bin` from JS with no engine running, so a launcher can paint four slots of two
games without instantiating anything. It is worth keeping, and so is the escape hatch: an engine
that cannot do it declares `'engine'` and `sdk.saves()` becomes sugar over `boot()`. Do not let
the scale collapse into a boolean.

# Extension · 2026-08-15 01h30 · Layer A dropped, `engine-specs.ts` as the single source, new test suite

**Summary of what changed since the plan above.** The contract was rewritten from scratch in
`src/truth.d.ts` → `src/truth.ts` → `src/engine-specs.ts`, and Layer A was removed entirely:
`src/manifest.ts`, `src/validate.ts` and `src/index.ts` are deleted. This supersedes phases **C**
(F1 · Layer A at 1.0) and most of **A**/**B** above — those described corrections to `engine.ts`,
which no longer exists.

## The decision

`engine-specs` defines **a common JS API, nothing more**. The manifest duplicated, as untyped
data, what the API now expresses as checked types: `options?: JSONSchema` is what `options()`
returns as a typed `PropertiesDefinition`; `AssetSpec` is what `assets()` describes; `capabilities`
is member presence. `validate.ts` and `schema/` existed only to police that data, so they go with
it — and with them the only runtime dependency, `zod`. The engine identity that was *not*
duplicated (`id`, `version`, `name`, `description`) survives as members of `EngineSDK`.

Cost, accepted knowingly: a host can no longer read what an engine needs without importing its
JS. Pre-boot discovery from a static JSON file is gone.

## The shape that landed

- `PropertyDefinition<Value>` + `PropertiesDefinition<T>` — a homomorphic mapped type with `-?`,
  so the getter's keys are the setter's keys and every descriptor is guaranteed present.
- Read/write as **overloaded methods**, not accessors: `config()` reads, `config(patch)` writes and
  chains. Accessors were tried and abandoned — a setter cannot return, so the chain is
  inexpressible with them.
- One bundled type parameter `P extends EnginePayloads` closes all four payloads at once, which
  makes the crossed-generics defect (§A.2 above) impossible: there is no order to get wrong.
- `EnginePayloads` members are `object`, not the four default interfaces, because a named
  `interface Rsdkv4Config` has no implicit index signature and would fail the constraint.
- `PromisePlay` extends `Promise` structurally: an engine may delegate to an internal promise
  rather than subclass, but must also carry `[Symbol.toStringTag]`.

## Tests

The old suite is deleted (`validate.test.mjs` tested a removed module; `demo.test.mjs` asserted
`manifest.id`). For a types-only package the tests that earn their place are:

1. `tests/types.test-d.ts` — compile-time conformance. A closed engine, a host driving it, and
   negative cases guarded by `@ts-expect-error`, which is self-policing: if a rejection stops
   happening, tsc fails on the unused directive.
2. `tests/engine.conformance.ts` — a fake engine that *implements* `EngineSDK`, proving the
   contract is implementable at all, which the plan above named as the real deliverable of F3.
3. `tests/package.test.mjs` — package integrity. Written because the previous suite passed 32
   tests green against stale `dist/` artifacts of deleted sources, and `make publish` is gated on
   exactly that suite. It asserts every `dist/*.js` has a source, that `exports`/`types` targets
   exist, and that the package declares no runtime dependencies.

`make build` now cleans `dist/` first, without which test 3 cannot be trusted.

## Extension · 2026-08-15 · four follow-ups

## Extension · 2026-08-15 · `EngineSurface`, new site routes, demo rewritten on the contract

**`EngineDataAccessors` → `EngineSurface`.** The old name stopped being true when `mount` joined
it: mounting is not accessing data, and it is the one member with no getter form. The interface
is now named for what it is — the members every carrier exposes.

**Site routes.** Typedoc moves from `site/api-docs` to `site/`, the demo from `site/` to
`site/demo/`. Typedoc cleans its own out dir, so `make site` runs it *before* copying the demo in,
never after. One real bug found while doing it: typedoc emits `navigationLinks` hrefs literally on
every page, so a relative `./demo/` resolved to `/interfaces/demo/` from a subpage. It is now the
absolute Pages URL — which means the link is dead under `make preview` on localhost, where the
demo is still reachable at `/demo/`. The same bug existed before the move (`"Demo": "../"` from
`/api-docs/interfaces/X.html`), it was just never noticed.

**Demo rewritten.** The old harness — `demo.js` (622 lines), `sdk.js`, `storage.js`,
`checksums.js` and four components — is deleted. What replaced it:

- `demo/demo.sdk.js` — a real engine, not a mock: four payloads closed with named types, getters
  returning descriptors, setters chaining, `boot()` idempotent, `start()` literally
  `boot().restart()`, and a structural `PromisePlay` that delegates to an inner promise. It is
  type-checked against the contract by `demo/tsconfig.json` (`checkJs`), so **the demo is the
  second conformance proof**, alongside `tests/engine.conformance.ts`.
- `demo/canvas-renderer.js` — the picture, knowing only a canvas and an `onFrame` callback.
- Five jq79 components. Each renders a list from one instance (`:each`) rather than one instance
  per item, because jq79's `render()` returns the same instance — N mounts from one component
  would fight over one fragment. jq79 has no `update(props)`, so `paint()` destroys and re-renders
  its mounts while `.on()` handlers are bound once at boot: they live on the component and survive
  `destroy()`, which is the bug the old demo documented at length.
- `demo/app.js` — the glue. Left out of `typecheck-demo`: it imports jq79 from a URL, which the
  compiler cannot resolve, and the conformance guarantee lives in `demo.sdk.js` anyway.

The demo now *demonstrates the contract* rather than merely using it: the header is the class's
static identity read with no engine constructed, the file pickers take their filter from each
asset descriptor's `allowedTypes`, and the four tables are the getters rendered as they arrive —
one component, no key names on the page. That last panel is the argument for the descriptor
existing at all.

**Not verified:** the page has not been opened in a browser. What was checked is that it serves
(`/` and `/demo/` both 200, all five components 200, jq79 reachable), that every id and component
`app.js` references exists, that both JS files parse, and that the engine type-checks against the
contract. Whether jq79 renders it correctly is unconfirmed.

### Correction · the demo is one root component, not a JS module

`demo/app.js` is replaced by `demo/app.html`. `index.html` is now a shell that mounts a single
root component:

```js
C79.fetch('./app.html').mount('body > main')
```

This is the right shape for jq79 and it deletes the machinery the module version needed. Composing
components declaratively — a PascalCase tag resolved from a scope variable, `@event` on the tag
subscribing to the child's `$emit` channel — means no mount handles, no `.on()` bound at boot, and
no destroy/re-render cycle: state is `let`s in the `:setup` script, and reassigning one repaints
whatever reads it. `demo.css` shrinks to the palette and the reset; the grid moves into
`app.html`, each panel's look into its own component.

One thing the component form cannot express as cleanly: the engine needs a real element for
`mount()`, and `:setup` runs before the template exists, so `onStart` reaches for
`document.querySelector('#stage')` at call time rather than holding a reference.

**Assumptions not verified in a browser**, and the first places to look if it does not come up:
`await import('./x.html')` inside `:setup` resolving relative to the component; PascalCase tags
resolving from setup-scope variables; `@event` on a child tag; and reassignment of a `let` being
what triggers the repaint. All five files serve 200 under `make preview`.

## Extension · 2026-08-15 · GitHub Actions restructured

`build.yml` gains `workflow_call` and loses its Pages deploy; `release.yml` calls it and owns
everything that publishes. Three jobs now, and the split is not cosmetic:

- **build** — `uses: ./.github/workflows/build.yml`. A release validates with the exact steps a PR
  ran, so there is no second copy of the checks to drift. It also runs `make site`, which is how a

  before the bump publishes the previous version. `make build` likewise runs *after* the bump.

**Behaviour change to be aware of:** the site no longer deploys on every push to main — only on
release. That is what moving Pages into `release.yml` means.

Two things checked rather than assumed: all five actions and their pinned majors exist
(`checkout` and `setup-node` are on v7 now, if a bump is wanted), and `make test && make site`
runs clean from a wiped `dist/`/`site/`, which is what CI does.

**Left alone deliberately:** the npm publish step has no `NODE_AUTH_TOKEN`. It never had one, and

## Extension · 2026-08-15 · `boot()` removed from the contract

`EngineSDK` now exposes `start()` alone. The reasoning, before it is forgotten: the one concrete
consumer `boot()` ever had is recorded above at line 153 — *"`sdk.saves()` becomes sugar over
`boot()`"* — and `saves` left with Layer A. Nothing in the repo called it for its own sake; the
only external call sat inside a `@ts-expect-error` proving something else.

What it takes with it: two normative rules that were stated and never covered (`boot()` is
idempotent, `start()` = `boot().restart()`), and `boot(init?)`, which was the third way to supply
payloads alongside the constructor and the accessors.

What was knowingly given up: the seam between paying an engine's startup cost and opening a
session. rsdkv4 boots on a pthread and reads its pack there (line 119), so that cost is real; a
host can no longer pay it early and make the first `start()` instant. Nor can a host read what
the engine actually resolved — a region deduced from a ROM header, geometry from a pack — without
a session running. If either turns out to matter, this is the decision to revisit, and the verb
comes back rather than being simulated with `start()`.

Implementations lose nothing: both reference engines keep a private `#boot()` and `start()` is
`#boot()` plus `restart()`. Removing it from the contract removed a public promise, not an
implementation. `dist/engine-specs.d.ts` now has zero mentions of it; all suites green.

## Extension · 2026-08-15 · `on()` / `off()` return to `EngineSurface` — plan

**Summary.** Events were dropped along with `engine.ts` in the rewrite; nothing replaced them, so
today a host has no way to hear anything from an engine — it can only ask. This plan puts `on()`
and `off()` back, as members of `EngineSurface` rather than of one carrier, and settles the
question the old contract never had to answer: how an engine declares events of its own now that
one bundled type parameter closes everything else.

### Why `EngineSurface` is the right home

`EngineSurface` is *"the members every carrier exposes"*. Subscribing belongs there for the same
reason `mount` does: a host subscribes before there is an engine (`new Sdk().on('error', report)`)
and again while one is running, and both must chain. Putting it on the surface makes the factory's
`on` and the live engine's `on` the same channel by construction, which is the rule the old
contract had to state in prose (*"handlers copied onto the play instance"*).

Like `mount`, these two are members with **no getter form** — there is no `on()` overload that
returns a listener list. The surface now has two such members, which is worth noting because it
weakens the reading that the surface is "four getter/setter pairs plus mount".

### A · How events are typed — the fifth member of the bundle

Three options were weighed. **Declaration merging** on a shared `EngineEventMap`, which is what
`engine.ts` did, is the one to avoid: merging is *global*, so twelve engines all widen the same
interface, and a host that imports two of them sees the union of events no single engine emits.
The bug it invites is `on('levelLoaded', …)` compiling cleanly against an engine that never emits
it. A **second type parameter** `EngineSurface<TSelf, P, E>` reintroduces exactly the
crossed-generics hazard recorded as defect §A.2 above — two parameters to transpose across four
carriers.

So events join the bundle, which is the shape this contract already committed to:

```ts
export interface EnginePayloads {
  config: object;
  options: object;
  assets: object;
  storage: object;
  /** Events this engine emits beyond the core set. Omit it and only the core set exists. */
  events?: object;
}
```

`events` is **optional**, unlike the other four, and that is deliberate: `DummyPayloads`,
`DemoPayloads` and any engine already written against 0.3.0 keep compiling, and an engine that
emits only the lifecycle events writes nothing. The core set is not in the bundle — it is unioned
in by the contract, so an engine cannot forget it or redefine it away:

```ts
export type EventsOf<P extends EnginePayloads> = CoreEvents<P> & NonNullable<P['events']>;
```

`NonNullable` is what makes the optional member work: when `events` is absent, `P['events']` is
`object | undefined`, and `object` contributes no keys to the intersection. It also covers the
engine that writes `events?:` in its own payload interface, which the `P extends { events: infer E }`
form would silently drop.

### B · The core set

`ready` does not come back — it fired when `boot()` completed, and `boot()` was removed above.
Per the approved selection, the core set is the minimum lifecycle plus `pause` / `resume`;
`progress` and `frame` are **left out** and stay engine-specific for now, declared through
`events` by any engine that wants them.

```ts
export interface CoreEvents<P extends EnginePayloads = DefaultPayloads> {
  /** A session opened, carrying the options it opened with. `restart()` emits it too. */
  start: { options: Partial<P['options']> };
  /** Emitted *and* rejected: a host that does not `await` is not left blind. */
  error: { error: Error };
  /** The engine went away — `destroy()` settled. */
  exit: void;
  /** Who asked, so a host can tell its own ESC menu from a visibility change. */
  pause: { owner: string };
  resume: { owner: string };
}
```

`start` carrying `Partial<P['options']>` rather than `payload: unknown` fixes the third type defect
listed in §A above, which was never addressed because events left the contract before it was.

`error: { error: Error }` and not the old `EngineError` with its `EngineErrorCode` union: that
union named storage backends, `readOnly` keys and manifest-`required` assets, none of which the
1.0 contract still has. A typed code union can come back when there is a list of codes this
contract can actually justify.

Dropping `progress` has a cost worth naming: it was the one event a *launcher* could use without
knowing the engine — paint a loading bar for any of the twelve. Nothing else in the core set is
useful before a session exists.

### C · Signatures

```ts
on<K extends keyof EventsOf<P>>(type: K, handler: (event: EventsOf<P>[K]) => void): TSelf;
off<K extends keyof EventsOf<P>>(type: K, handler: (event: EventsOf<P>[K]) => void): TSelf;
```

The handler on `off` is **required**, as in `EventTarget` and in the old contract. A convenience
`off(type)` that removes every listener for a type is a footgun in a page where two components
subscribed independently: one unsubscribing silences the other.

Constructor parity, which this repo states as a rule and pins with a test
(`tests/types.test-d.ts`, *"whatever the chain takes, the constructor takes"*):

```ts
export type EngineEventHandlers<P extends EnginePayloads = DefaultPayloads> = {
  [K in keyof EventsOf<P>]: (event: EventsOf<P>[K]) => void;
};

export interface EngineInit<P extends EnginePayloads = DefaultPayloads> {
  // …
  on?: Partial<EngineEventHandlers<P>>;
}
```

This is the one place a handler is supplied as a map rather than a pair, which is what makes
`new Sdk({ on: { error: report } })` and `new Sdk().on('error', report)` the same call.

### D · Normative rules to write into the tsdoc

1. Handlers registered on the factory are live on the engine the factory opens — one channel, not
   two. A host subscribes once, before `start()`.
2. `error` is emitted **and** the promise rejects. Both, always.
3. `start` fires on every session open, `restart()` included.
4. `exit` fires once, when `destroy()` settles.
5. Subscribing is chainable and unordered: `on()` before or after `mount()` is the same.

### E · What this ripples into

`EngineSurface` gains members, so everything that `implements` it stops compiling until it grows
them. That is the bulk of the work, not the type change:

| file | change |
| --- | --- |
| `src/engine-specs.ts` | `CoreEvents`, `EventsOf`, `EngineEventHandlers`, `events?` on `EnginePayloads`, `events` on `DefaultPayloads`, `on`/`off` on `EngineSurface`, `on?` on `EngineInit` |
| `tests/engine.conformance.ts` | a real emitter on `DummyPlay` and `DummySDK`, `on`/`off` through `hydrate()`, handlers from `init.on` |
| `tests/types.test-d.ts` | positive cases (payload narrowing per event, chaining on both carriers, constructor parity) and `@ts-expect-error` for an unknown event name, a mistyped handler parameter, and `off()` without a handler |
| `demo/demo.sdk.js` | same, in JSDoc. `DemoPlay.pause()` / `resume()` are private members today — they become emitters of the core `pause` / `resume` events, so the demo exercises them |

| `README.md` | the events section it has never had |

Verification is `make test` (build + `typecheck-tests` + `typecheck-demo` + package integrity) plus

a browser.

### Open question, not blocking

Whether an engine may emit an event the contract does not know about — a `string` type that is not
in `EventsOf<P>`. Closed maps say no, and that is the default here. The alternative is an index
signature on `EngineEvents` for the open-payload case only, which is already what `DefaultPayloads`
gets for free: an engine that closes nothing can emit anything, an engine that closes its payloads
declares its events. That asymmetry looks right, but it is worth a second look during implementation.

### Revision · a shipped `EventEmitter`, and why it is composed rather than extended

Proposed during review: ship the emitter itself, not only its type.

```js
class EventEmitter {
  on(eventName, listenerFn)
  off(eventName, listenerFn)
}
```

Worth doing — it would be the **first executable thing in this package**, which is what §B above
argues has been missing since the start (*"twelve engines are meant to inherit that, not
re-derive it"*). The bookkeeping is small but it is the kind everyone gets subtly wrong: iterating
a copy so a listener that calls `off()` mid-emit does not corrupt the loop, de-duplicating a
listener registered twice, and keeping one throwing listener from silencing the rest.

Two things break if it is used as a base class, though, and both point the same way.

**1. `extends` cannot reach the carrier a host actually holds.** `PromisePlay` is not a class in
either reference engine — `hydrate()` returns an object literal, deliberately, because the contract
allows a structural promise instead of a `Promise` subclass. It cannot extend anything. A base
class would cover `DummySDK` and `DummyPlay` and miss the object returned by `start()`.

**2. Three emitters are three channels.** If the factory and the live engine each extend the class,
`sdk.on('error', …)` and `play.on('error', …)` write to different lists, and rule D.1 — handlers
registered on the factory are live on the engine it opens — goes back to being hand-written in
every engine. That is precisely the re-derivation the emitter exists to stop.

**And the hallmark of the fix: chaining `on` through the promise registers too late.** §C above had
`PromisePlay.on` going through `chain()` like `mount`, so the handler would bind only once the
inner promise resolved. `sdk.start().on('error', report)` would then miss an error thrown *during*
start — the one error a host most wants. Not a flaw in the emitter proposal; a flaw in the plan the
proposal exposed.

All three dissolve with one channel, owned by the factory, created before the engine exists and
shared with everything downstream:

```ts
export class EventEmitter<E> {
  on<K extends keyof E>(type: K, listener: (event: E[K]) => void): this;
  off<K extends keyof E>(type: K, listener: (event: E[K]) => void): this;
  emit<K extends keyof E>(type: K, event: E[K]): void;
}
```

Held privately (`#events = new EventEmitter()`), passed to the `Play`, closed over by `hydrate()`.
Each carrier keeps a two-line delegation that returns its own `TSelf`, which is what the chain
requires and what no shared class can return for it. `on` and `off` become **synchronous on every
carrier, including `PromisePlay`** — a new normative rule, and a better one than the plan had.

Composition also keeps `emit` out of the public API. If an engine extended the class, a host could
call `play.emit('error', …)` and forge an engine event.

**What it costs.** The package stops being types-only: `dist/engine-specs.js` stops being
`export {}`, README's first line stops being true, and engines gain a *value* import where they had
`import type`. Version skew would put two copies of the class in one bundle — benign here, because
a channel is per-engine-instance and no cross-copy communication exists, but worth stating rather
than discovering. No new dependencies, so `package.test.mjs` stays green; it gains an assertion
that the emitter is really in the emitted JS, since a types-only regression would otherwise pass.

**Not a mandate.** The contract stays structural: an engine that already owns an emitter — common
in Emscripten builds — delegates to its own and satisfies `EngineSurface` just as well. `once()` is
deliberately left out until something asks for it.

This is also a precedent worth naming: with runtime code in the package, the `EngineSDKBase` that
§B wanted (the chain, the freeze, the cumulative payload) stops being a different kind of change
and becomes more of the same one.

### Revision · `EngineSDKConstructor extends EventEmitter` — measured, not argued

Also proposed during review. It reads like "the engine class is an emitter", and the parallel with
the identity decision is real: a launcher reads `Rsdkv4SDK.id` without constructing, so why not
`Rsdkv4SDK.on(…)`. Three things were checked with `tsc` and `node` rather than reasoned about,
because the answers are not the ones the syntax suggests.

**1. With `EventEmitter` as a class, the extension is unsatisfiable.** `EngineSDKConstructor`
describes the *static* side, so the inherited members land on the statics — and ES private fields
make the class type nominal:

```
error TS2741: Property '#listeners' is missing in type 'typeof EngineA' but required in type 'SDKCtor'.
error TS2739: Type 'typeof EngineB' is missing the following properties from type 'SDKCtor': #listeners, on, off, emit
```

`EngineB` there is a class that *does* `extends EventEmitter`. It still fails, and that is the
crux: extending puts `on`/`off` on instances, while the constructor interface asks for them on the
class object. The two never meet.

**2. Drop the private field and it compiles — into the wrong shape.** With a structural
`EmitterShape` interface, a class satisfies it by declaring `static on` / `static off`. Then
`Rsdkv4SDK.on('start', …)` type-checks and `play.on('start', …)` does not exist at all, at either
level — `tsc` rejects it, and Node confirms with `TypeError: (intermediate value).on is not a
function`. Which is the opposite of the original request: `on`/`off` on `EngineSurface`, the
members *every carrier* exposes.

**3. Inheriting the channel through statics is a runtime landmine.** The natural implementation —
`static #channel` on a base, `this.#channel` inside a static method — **compiles clean** and then
throws on the first call from a subclass:

```
TypeError: Cannot read private member #channel from an object whose class did not declare it
```

because `this` in `EngineB.on()` is `EngineB`, which is not the class that declared the field.
Making the field non-private fixes the crash and replaces it with a quieter bug: verified
`EngineB.channel === EngineC.channel` → `true`, so **every engine class in the page shares one
listener list**. A host subscribing to one engine's `error` hears every engine's.

**What survives of the idea.** The property worth wanting — subscribe before anything is
constructed — is already delivered by the shared channel of the previous revision, without the
ambiguity: `new Sdk().on('error', report)` registers on a channel that exists before the engine
does. And a static channel could not carry the core set meaningfully anyway: `start`, `error`,
`exit`, `pause` and `resume` all describe *a session*, and a class-level listener has no way to
tell which instance emitted, since a page may construct two factories of the same class.

**What it suggests instead.** If the goal behind it is that an engine should not have to *write*
`on`/`off` at all, the shape that delivers it is not the constructor interface but the concrete
base class §B has wanted all along — `EngineSDKBase`, owning the channel, the delegation and the
`hydrate()` that carries it, so an engine inherits the members instead of implementing them. That
is a larger change than this session, and it is the natural next one.

### Approved · go with `EngineSDKBase`, in two stages

Accepted during review. The staging below is not hedging — it is the difference between factoring
out duplication that has been *measured* and guessing at it.

**Stage 1** — the contract change already planned above: `CoreEvents` / `EventsOf` / `events?` in
the bundle, `on`/`off` on `EngineSurface`, `on?` on `EngineInit`, the shipped `EventEmitter`, and
both reference engines wiring the shared channel **by hand**. Small, verifiable, leaves the repo
green, and it is a prerequisite of Stage 2 either way.

**Stage 2** — `EngineSDKBase`, implemented *after* Stage 1 lands, because a base class is worth
exactly what it deletes from the engines that adopt it, and that cannot be counted until the
event plumbing exists in both of them. Writing it twice first is the cheap way to learn what the
seam is.

#### What is provably duplicated today

Measured in the working copy, not assumed:

- **`hydrate()` is the same function twice.** `tests/engine.conformance.ts:154-190` and
  `demo/demo.sdk.js:250-284` differ in language (TS casts vs JSDoc) and in nothing else — same
  `chain`, same four getter/setter ternaries, same `[Symbol.toStringTag]`, same delegation.
- **Every `default` is written twice, in both engines.** `#config: DummyConfig = { region: 'us' }`
  alongside `default: 'us'`; `#config = { baseWidth: 320, baseHeight: 256 }` alongside
  `default: 320` and `default: 256`; `#options = { player: 'sonic', slot: 0 }` alongside
  `default: 0`. Two sources of truth for one fact, in a package whose entire purpose is to have
  one. Nothing catches the drift.
- **The four getter/setter bodies** are the same `arguments.length === 0` dance eight times per
  engine — four on the SDK, four on the Play.
- **`start()` = `hydrate(Promise.resolve(this.#boot())).restart(options)`** and the
  `#play ??= new Play(#init)` idempotence, identical in both.

What is *not* duplicated, and therefore what the seam must leave to the engine: the descriptor
metadata, and the engine's actual behaviour (renderer, memfs, wasm).

#### The shape

The engine declares its properties as data, minus the values — the base composes the descriptors
and seeds the initial state from the same `default`, which is what collapses the two sources of
truth into one:

```ts
export type PropertySpec<Value> = Omit<PropertyDefinition<Value>, 'value'>;
export type PropertiesSpec<T> = { [K in keyof T]-?: PropertySpec<T[K]> };
export interface EngineSpec<P extends EnginePayloads> {
  config: PropertiesSpec<P['config']>;
  options: PropertiesSpec<P['options']>;
  assets: PropertiesSpec<P['assets']>;
  storage: PropertiesSpec<P['storage']>;
}
```

`-?` carries over from `PropertiesDefinition`, so an engine cannot forget to describe a key.

The base owns state, the cumulative merge, the descriptors, the channel, `hydrate()`, `start()`
idempotence, and the rule that `error` is emitted *and* rethrown. The engine implements what only
it knows:

```ts
protected abstract open(options: Partial<P['options']>): void | Promise<void>;  // start / restart
protected abstract close(): void | Promise<void>;                                // destroy
protected mounted(target: HTMLElement): void {}                                  // optional
protected patched(kind: keyof EngineSpec<P>, patch: object): void {}             // optional, live apply
protected emit<K extends keyof EventsOf<P>>(type: K, event: EventsOf<P>[K]): void; // provided
```

Named `open`/`close`/`mounted`/`patched` rather than `onStart`/`onDestroy` deliberately: a
protected `onStart` sitting next to the public `on('start', …)` is a name collision waiting to
confuse. `emit` is `protected` and provided by the base — the engine emits its own events, a host
cannot forge one.

#### The one fork left open

Whether the engine writes **one class or two**. Two (`EngineSDKBase` + `EnginePlayBase`) mirrors
the contract's own split and is the direct translation of what exists. One class is nicer to
write, but requires the base to manufacture the `EnginePlay` as a facade over the engine
instance — and a facade drops members the contract does not know about, which would break
`DemoPlay.pause()` / `resume()`, the two members the demo's ESC menu calls. A middle form worth
trying during Stage 2: the engine writes only the Play subclass, and the SDK comes from a helper
(`engineSDK(DemoPlay, { id, version, spec })`) that returns an `EngineSDKConstructor`. Decide it
against the real diff once Stage 1 is in, not now.

#### Adoption stays optional

The contract remains structural. `EngineSDKBase` is a convenience an engine may ignore — an
Emscripten build with its own emitter and its own state keeps satisfying `EngineSDK` without
touching it. The conformance proof stays `tests/types.test-d.ts`, not "extends our class".

**Status: Stage 1 approved and implemented — walkthrough below. Stage 2 designed above, not started.**

# Extension · 2026-08-15 · `detail` on every event, and Stage 2

Two changes approved together, and implemented in this order on purpose: the event shape changes
what an engine writes, so changing it *before* the base classes means both reference engines are
rewritten once instead of twice.

## A · The payload moves under `detail`

Requested shape, `CustomEvent`'s:

```js
sdk.emit('foo', payload)
sdk.on('foo', (event) => { event.detail === payload })
```

So a listener no longer receives the payload — it receives an **event object** carrying it:

```ts
export interface EngineEvent<K = PropertyKey, Detail = unknown> {
  readonly type: K;
  readonly detail: Detail;
}
```

`type` comes along because it is free and it is what lets one listener serve several events. The
map `EventsOf<P>` keeps its shape but its values are now **details**, not events — which lets the
core set shed a layer of wrapping it only had because there was nowhere else to put the payload:

| | before | after |
| --- | --- | --- |
| `start` | `{ options: Partial<Options> }` | `Partial<Options>` — `event.detail` *is* the options |
| `error` | `{ error: Error }` | `Error` — `event.detail` *is* the error |
| `pause` / `resume` | `{ owner: string }` | unchanged; the owner is one field of a payload that may grow |
| `exit` | `void` | unchanged; `event.detail` is `undefined` |

The event object is built once per `emit` and **frozen**: it is handed to every listener in turn,
so without freezing the first listener could rewrite what the second one reads.

## B · Stage 2 · the fork, closed against the real code

The plan left one question for the diff to answer: does an engine write one class or two? Reading
what Stage 1 actually produced settles it, and it also corrects something the plan got wrong.

**What the plan got wrong.** It said a facade "drops members the contract does not know about,
which would break `DemoPlay.pause()`". That is only true of the *promise* wrapper — and that was
already true before any of this: `hydrate()` has never carried an engine's own members, so
`sdk.start().pause()` was never possible in either engine. `await sdk.start()` resolves to the real
play instance, `pause()` included. So the facade objection was smaller than stated.

**What decides it instead** is that one class cannot serve both roles regardless: `config(patch)`
returns `this` on the factory and `PromisePlay` on the live engine, and no single method has two
return types. So the engine writes a `Play`, and the only question is whether it writes the
factory too or gets it generated.

**Decision: two base classes, both `abstract`, engine subclasses both.** A generated factory
(`engineSDK(DemoPlay, { id, version, spec })`) is nicer to write but hostile to the thing that
makes the demo worth having — it is checked with `checkJs`, and a generic factory function
returning a class is exactly where JSDoc generics stop being expressible. A base class an engine
`extends` is `@extends {EnginePlayBase<DemoPayloads>}` and nothing more. The contract's own split
is mirrored rather than hidden, and `EngineSDKConstructor` stays satisfied by a real class with
real statics.

The engine's factory subclass is small enough that the objection loses force:

```js
class DemoSDK extends EngineSDKBase {
  static id = 'dummy-canvas-sdk'
  static version = '0.1.0-demo'
  createPlay(init, events) { return new DemoPlay(init, events) }
}
```

**Where the spec lives: on the `Play`, not the factory.** Both need it — the factory answers
`config()` before an engine exists — and duplicating it would reintroduce the two-sources-of-truth
bug this whole exercise exists to kill. The factory gets it the way both engines already answer
pre-boot reads: by holding a pending `Play`.

### The seam, as it landed

An engine declares `EngineSpec` — descriptors minus their values — and implements `open`, `close`,
and optionally `mounted` and `patched`. The base owns state, the cumulative merge, the descriptors,
the channel, `hydratePlay()`, `start()` idempotence, and the rule that a failing hook both rejects
the chain and emits `error`.

The spec is a **constructor argument**, not an abstract field, and that is not style: a subclass
field initialiser runs after `super()`, so `protected abstract spec` would still be `undefined`
while the base constructor seeded state from it. Passing it up makes the ordering trap impossible
rather than merely avoided.

`hydratePlay` and `EventEmitter` are exported separately, so an engine that wants the pieces
without the base classes can have them. Adoption stays optional; the contract is still structural.

### Three bugs found by writing the tests, not by reading the code

1. **`#emitCore` called `emit` unbound.** Extracting the method into a variable to cast it lost
   `this`, so every core event threw `Cannot read properties of undefined (reading '#listeners')`.
   Nine tests went red at once. The fix casts the channel and keeps the call a method call.
2. **`new Sdk({ mount: el }).start()` never told the engine where it was.** The base recorded the
   target in its constructor and nothing ever called `mounted()` — so the demo would have created
   no canvas at all. It could not simply be called from the constructor either: `mounted()` is
   overridable and a subclass's own fields are still uninitialised at that point. It is now
   deferred to the first `restart()`, which is also the moment that makes
   `new Sdk({ mount: el }).start()` and `new Sdk().mount(el).start()` the same call — the rule the
   contract states for the whole surface, and which now has a test.
3. **A claim in the tsdoc was simply false.** `emit` being `protected` was documented as meaning a
   host "cannot forge an engine event". TypeScript erases `protected`; only `#private` survives to
   runtime, so plain JavaScript can still call it. The doc now says what is true — a compile-time
   guard, not a capability boundary — and a test pins the behaviour so nobody re-derives the wrong
   belief.

`tests/engine-base.test.mjs` is new: 18 cases covering the rules the base now implements on behalf

cumulative merging, one engine per factory, mount ordering and idempotence, `destroy` emitting
`exit` once, and errors arriving **both** ways. Each of these was previously a sentence in a spec
that each engine re-derived; there is one implementation now, so there can be one test.

`tests/shared-channel.test.mjs` was rewritten onto the real base classes instead of a hand-copied

counterfactual — a registration routed through the chain, asserted to **miss** the event — which is

`tests/event-emitter.test.mjs` grew the envelope cases: the detail is the payload identically and
