# 2026-08-15 12h39 · The TypeDoc header, in the demo

Presentation only. Nothing in `src/engine-specs.ts` moves; the contract, the tests and the
published package are untouched.

## What was asked

1. In the generated reference, `button#tsd-search-trigger` sits **immediately right of
   `a.title`**, instead of far right next to the menu trigger.
2. The demo wears **that same header** — minus the search trigger, which it cannot have: the
   demo page carries no search index and does not load TypeDoc's `main.js`, so a trigger there
   would open nothing.

## What is there now

**The reference.** TypeDoc emits one flex row, `.tsd-toolbar-contents`, in DOM order
`a.title` → `#tsd-toolbar-links` → `button#tsd-search-trigger` → `dialog#tsd-search` →
`a#tsd-toolbar-menu-trigger`. The title carries `margin-right: auto`, and that single
declaration is what pushes everything else to the far right.

Everything TypeDoc ships lives inside `@layer typedoc` (`site/assets/style.css:1`). Unlayered
rules therefore beat it whatever their specificity — no `!important`, no specificity games.
That is what makes both halves of this cheap.

**The demo.** Its header is `demo/components/engine-header.html`: the engine's static identity
on the left, a version pill and an "API reference" link on the right, painted from the demo's
own palette in `demo/demo.css`.

**Why reuse is even possible.** The demo only ever runs from `site/demo/` — `demo.sdk.js`
imports `../src/engine-specs.js` as a *value*, which is why `make site` copies the built JS to
`site/src/`. So `../assets/style.css` is always next to a running demo. Nothing here works from
a bare `demo/` checkout, and nothing here made that newly true.

## A · The reference: the trigger moves next to the title

New file `typedoc.css` at the repo root, wired as `"customCss": "typedoc.css"` in
`typedoc.json`. TypeDoc copies it to `site/assets/custom.css` and links it after `style.css`.

```css
/* Unlayered on purpose: all of TypeDoc's own CSS is inside `@layer typedoc`, so these win
   without `!important`. */
.tsd-toolbar-contents > .title            { order: 1; margin-right: 0.5rem; }
.tsd-toolbar-contents > #tsd-search-trigger { order: 2; margin-right: auto; }
.tsd-toolbar-contents > #tsd-toolbar-links  { order: 3; }
.tsd-toolbar-contents > #tsd-toolbar-menu-trigger { order: 4; }
```

The `margin-right: auto` **moves** from the title to the trigger: that is the whole trick, and
it is what keeps the links and the menu flush right while the trigger sits by the title.
`dialog#tsd-search` needs no rule — `main.js` opens it with `showModal()`, so it is in the top
layer and out of the flex flow, and a closed `dialog` is `display: none`.

Cost, stated rather than buried: `order` is **visual only**. Tab order stays title → links →
search. The alternative is a DOM move in `customFooterHtml`, where a fix-up script already
lives; it keeps tab order matching what the eye sees, but it depends on JS and on the header's
current markup surviving a TypeDoc upgrade. Recommending the CSS.

## B · The demo wears the same bar

- `demo/index.html` links `../assets/style.css` **before** `./demo.css`, and runs TypeDoc's
  one-line theme bootstrap (`document.documentElement.dataset.theme = localStorage.getItem(
  "tsd-theme") || "os"`), so the bar honours the theme chosen in the docs rather than starting
  from scratch.
- New `demo/components/site-toolbar.html`, reproducing TypeDoc's markup exactly:
  `header.tsd-page-toolbar > div.tsd-toolbar-contents.container` with `a.title` → `../` and
  `#tsd-toolbar-links` → Reference · GitHub. No search trigger. **No version in the title
  text** — TypeDoc gets it from `package.json`, a hand-written copy in the demo would drift.
- `engine-header.html` keeps the engine identity and loses its "API reference" pill, which the
  toolbar now carries. Two bars stack: site chrome above, engine identity below.

Because the layer rule cuts both ways, the demo's own styles (unlayered) keep winning over
TypeDoc's base rules for `body`, headings, tables and the rest. Adopting the stylesheet
therefore restyles only what the demo never styled itself.

## Decided — 2026-08-15 12h45

Both recommendations taken: **CSS `order` via `customCss`** for the reference, and the demo
**follows the docs theme**.

**The demo's palette.** TypeDoc's theme is `data-theme` off `localStorage`; the demo's is
`prefers-color-scheme`. Left alone they can disagree — light docs on a dark OS gives a light bar
over a dark demo.

- *Follow the docs* — map the demo's variables onto TypeDoc's (`--bg: var(--color-background)`,
  `--panel: var(--color-background-secondary)`, `--text: var(--color-text)`,
  `--muted: var(--color-text-aside)`), keeping `--accent: #ff007f` as the demo's own signature.
  One theme switch, in the docs sidebar, drives both pages. ~8 lines in `demo.css`.
- *Leave it* — only the bar follows the docs theme; the demo body keeps its own palette.

## Walkthrough · as built

`typedoc.css` (new, wired as `customCss`) carries both reference-side changes: the toolbar
reorder as planned, and — asked for mid-session — the vertical rhythm moved off
`.container-main` and onto the columns. That second one zeroes
`--dim-container-main-margin-y` rather than the `margin` property, because the same value
feeds `.container-main`'s `min-height` and the sticky menus' `top` and `max-height`; killing
the margin alone would have left three sums subtracting a gap that no longer existed. The
columns get `padding-block: 2rem`, the menus only above 770px — below that they are inside a
drawer with padding of its own — plus `box-sizing: border-box`, which TypeDoc sets per
component and not on these two.

Demo side, four asks landed on top of the original one:

- **The bar is TypeDoc's**, markup and stylesheet both, in a new `site-toolbar.html`. No
  search trigger.
- **`a.title` carries the version**, and does not hard-code it: `make site` writes
  `site/demo/package-version.js` from `package.json` — the same source TypeDoc quotes — and
  `app.html` imports it inside a `try`, so a bare `demo/` checkout shows the name alone
  instead of a stale number. The file is generated into the gitignored `site/`, never
  checked in.
- **`header.engine-header` became `footer.engine-header`**, moved below everything and
  stripped of its `h1`; `border-bottom` became `border-top`. The engine's `name` still
  reaches the reader as the document title. Its `id` no longer appears anywhere on the page
  — the `h1` was the only place it was shown.
- **The assets section is a row, not a card**: key and hints left, actions right, tighter
  padding — roughly half the height. **Lifecycle moved under `#stage`**, which also gave it
  one row of buttons instead of two. That required `aside section` to become a `.panel`
  class, since the panel now lives in the other column.

### Found by opening the page, not by reading it

**Component styles are global.** jq79 puts each component's `<style>` into the page
unscoped, so `engine-header`'s bare `header { display: flex; … }` reached the new toolbar,
made a flex container of it and centred the whole bar — the title's `margin-right: auto` had
no free space left to consume. The component's rules are now scoped to `.engine-header`. The
other components' bare selectors (`button`, `table`, `td`, `h3`) do not touch the toolbar,
so they were left alone; they remain a trap for the next component that reuses an element
name.

**`word-break: break-all`** on the picker's paragraphs, harmless while each sat on its own
line, broke prose mid-word once the text shared a row with the button. Now
`overflow-wrap: anywhere`, which still breaks a long file name.
