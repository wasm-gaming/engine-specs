# A virtual gamepad for phones and tablets

2026-11-15 · follows [2026-11-13.usability-scheme-input-and-app-contract.completed.md](2026-11-13.usability-scheme-input-and-app-contract.completed.md).

**Status:** Proposal — awaiting the owner's approval before any code changes.

## Why

On a phone or a tablet there is no keyboard and usually no gamepad, so neither the menus
(`createInput()`) nor the games can be played. The owner asked for "mando virtual para mobile y
tablet". engine-specs is where the usability scheme and its runtime live, and the one package
every engine and the launcher already depend on, so the virtual pad belongs here too — one pad,
the same everywhere, like the menus.

## What the engines read today (measured)

| engine | input path | what a virtual pad needs |
| --- | --- | --- |
| rsdkv3, rsdkv5, fbneo | SDL2 (`-sUSE_SDL=2`) → the browser Gamepad API | a gamepad in `navigator.getGamepads()` |
| blastem | SDL2 ("gamepads work through SDL2", README) | same |
| ppsspp | SDL3 (`-sUSE_SDL=3`) | same |
| snes9x, mGBA, geolith | their JS calls `navigator.getGamepads()` | same |
| rsdkv4 | SDL2, **and** host-driven input: `play.input.claim(buttons)` | either |
| jgenesis | its SDK (`src/jgenesis.sdk.ts`) — to be checked | — |

So the one bridge that reaches almost every engine without touching it is the **Gamepad API**: a
virtual pad that shows up in `navigator.getGamepads()` with the W3C *standard* mapping, which is
exactly what `UI_PADMAP` and every engine's gamepad defaults already speak.

## Design

### 1. The pad: `createTouchPad(target, options)` → `TouchPad`

A DOM overlay drawn into `target` (no framework, no images, no runtime dependency — the package
stays dependency-free). It **is** a `UiGamepadLike`: `buttons[]` (17, standard mapping) and
`axes[]` (4), read at poll time.

- **Controls**: d-pad (left), face buttons (right), Start / Select (bottom centre), shoulders
  (top corners), and a **pause button** (top right). Which ones are drawn, and their labels, come
  from a layout (§3).
- **Multitouch with Pointer Events**: each `pointerId` is tracked on its own, with
  `setPointerCapture`; a finger **slides** from one button to another (B → A without lifting), and
  the gap between two adjacent face buttons presses both (the arcade "roll"). The d-pad is
  8-way: the angle from its centre in 45° sectors, a dead zone in the middle.
- **Never a stuck button**: `pointerup`, `pointercancel`, `lostpointercapture`, `blur` and
  `visibilitychange` release what that finger held — the same rule as rsdkv4's host input (a
  failure leaves a dead button, never a held one).
- **No tap lost**: a press shorter than a frame stays pressed until the next animation frame, so
  any consumer polling once per frame sees it at least once.
- **The page does not fight back**: `touch-action: none`, `user-select: none`,
  `-webkit-touch-callout: none`, `overscroll-behavior: none`, no context menu — no scroll, zoom,
  text selection or iOS callout while playing.
- **Feel**: pressed state drawn instantly (no transition on press); `navigator.vibrate(8)` on
  press where it exists (Android; iOS Safari has none — silently skipped). Opacity and size are
  options, so a host can offer them as settings.
- **Readable** (UX.md rule 8): every target ≥ 48 px, laid out inside the safe areas
  (`--wg-safe-*`), drawn with `UI_TOKENS`.
- **Orientation**: landscape overlays the controls on both sides of the game; portrait puts them
  in a band below it. The pad reports the space it takes (`insets`) so the host can fit the
  canvas into what is left.
- **When it shows**: on `(pointer: coarse)` devices, from the first touch. It hides when a
  physical gamepad connects or a key is pressed, and comes back on the next touch.

```ts
interface TouchPad extends UiGamepadLike {
  readonly id: string;               // 'wasm-gaming virtual pad (STANDARD GAMEPAD)'
  readonly mapping: 'standard';
  readonly connected: boolean;       // false while hidden
  layout(layout: TouchLayout): void;
  show(): void;
  hide(): void;
  readonly insets: { top: number; right: number; bottom: number; left: number };
  onPause(listener: () => void): () => void;
  destroy(): void;
}
```

The pointer → button logic (hit-testing, d-pad sectors, sliding, latching, release on cancel) is
pure functions over rectangles and points, separate from the DOM, so it is tested with
`node:test` like `ui.test.mjs`; only the drawing needs a browser.

### 2. Bridges

- **Menus**: `createInput({ gamepads: () => [...navigator.getGamepads(), pad] })` — nothing new
  in `createInput()` beyond that option, which already exists.
- **Pause**: the pause button does **not** fake Select + Start (the engine, which polls the same
  pad, would see Start and act on it). Instead `UiInput` gains `trigger(action, detail)`, and the
  host wires `pad.onPause(() => input.trigger('menu', { source: 'touch', repeat: false }))`.
  `UiActionDetail.source` gains `'touch'`, so hints can show touch glyphs. Both additive.
- **Engines**: `exposeAsGamepad(pad)` → `release()`. Wraps `navigator.getGamepads()` so it
  returns the real pads plus the virtual one in the first free index, and dispatches
  `gamepadconnected` / `gamepaddisconnected` (an `Event` carrying a `gamepad` property — the shape
  Emscripten's handler reads) when the pad shows / hides. Installed before the engine starts, so
  SDL's start-up enumeration already finds it. `release()` restores the original function.
- **Engines with host-driven input** (rsdkv4's `claim()`) may read the pad directly instead; the
  engine app decides.

### 3. Layouts: the engine says which buttons it has

`TouchLayout = { dpad: boolean; buttons: Partial<Record<TouchButton, string>> }`, where
`TouchButton` is a standard-mapping button (`a b x y l r l2 r2 start select`) and the string is
its label. Presets, as data:

| preset | face buttons (label → standard button) |
| --- | --- |
| `TOUCH_LAYOUTS.megadrive3` | A B C, in a row |
| `TOUCH_LAYOUTS.megadrive6` | A B C / X Y Z, two rows, + Mode |
| `TOUCH_LAYOUTS.neogeo` | A B C D, in an arc |
| `TOUCH_LAYOUTS.snes` | A B X Y diamond + L R |
| `TOUCH_LAYOUTS.gba` | A B + L R |
| `TOUCH_LAYOUTS.gameboy` | A B |
| `TOUCH_LAYOUTS.rsdk` | one jump button (A) — every Sonic jump button is the same action |
| `TOUCH_LAYOUTS.psp` | △ ○ ✕ □ + L R |

Which standard button each label maps to is the engine's existing gamepad default, so no engine
remaps anything. The contract gains, additively: `EngineApp.touchLayout?: TouchLayout | ((game)
=> TouchLayout)` (a multi-system engine, fbneo, picks by game), and `EngineAppHost.touch?:
TouchPad` — **the host creates the pad** (like `input`), the app sets its layout and shows it while
the game runs, and hides it while one of its menus is open (menus are tapped directly).

### 4. Menus by touch (UX.md, new section "Touch")

- Every focusable element answers a tap: it takes the focus and acts as `accept`.
- The pause button replaces Select + Start; it is always visible in game, top right.
- The virtual pad is hidden while a menu is open; `back` is the menu's own on-screen back button.
- Hints show the touch glyph when the last action came from `'touch'`.
- Rule 7 already covers text: nothing needs a keyboard.

### 5. Demo

`demo/touchpad.html`: every preset, live button and axis state, and the actions `createInput()`
delivers — open it on a phone (or with Chrome's device toolbar) to try it.

## Out of this record (follow-ups, one per repo)

- Each engine app: declare `touchLayout`, show / hide the pad — rsdkv4, rsdkv3, rsdkv5, fbneo,
  blastem first (the engines that already have an app), then the rest as they reach contract 1.0.
  Each checks on a real phone that SDL sees the virtual pad; if one does not (SDL's mapping
  lookup keys on the `id` string), that engine falls back to host-driven input.
- The launcher (play.germade, not attached to this session): create the pad, pass `host.touch`,
  fit the canvas to `pad.insets`, a settings entry for opacity and size.
- ROADMAP row in wasm-gaming.github.io.

## Version

All additive (new exports, optional contract fields, a new `UiInput.trigger`, a new `source`
value): **0.5.0** — a minor, since `UiActionDetail.source` widens and an exhaustive `switch` over
it in a consumer would need a new case.

## Testing

- `node:test`: d-pad sectors and dead zone; slide between buttons; the gap pressing two buttons;
  multitouch (d-pad + button + another button); release on cancel / blur / hide; a press shorter
  than a frame still read once; `exposeAsGamepad` adds and removes exactly one pad and restores
  the original `getGamepads`; `trigger('menu')` reaches listeners while suspended.
- Browser: the demo on a phone and on Chrome's device emulation (portrait and landscape,
  screenshots), and one SDL engine (rsdkv5 or fbneo) actually moving with the virtual pad.

## Open decisions (owner)

1. **Where the pad is created**: by the host and passed as `host.touch` (recommended — one pad,
   like `input`) or by each engine app.
2. **Bridge to engines**: the Gamepad API wrapper (recommended — no engine changes) or a
   host-driven input API in every engine, like rsdkv4's `claim()`.
3. **Pause button vs Select + Start on touch**: dedicated button (recommended).

### One layout per system, keyed by the system — not by the engine

`TOUCH_LAYOUTS: Record<TouchSystem, TouchLayout>`, with `TouchSystem = 'megadrive' | 'neogeo' |
'snes' | 'gba' | 'gbc' | 'gb'`. The same system on another core (Mega Drive on jgenesis) gets the
same pad. Each button: its label, the standard-mapping button it presses, and its place in the
cluster.

| system | right cluster | shoulders | centre |
| --- | --- | --- | --- |
| `megadrive` | **6 buttons**: A B C (bottom row), X Y Z (top row, smaller) — the launcher already plugs two 6-button pads; a 3-button game ignores X Y Z | — | Start |
| `neogeo` | A B C D, in the AES pad's slanted row | — | Start, Select |
| `snes` | A B X Y diamond, in Nintendo's positions (A right, B bottom, X top, Y left) | L, R | Start, Select |
| `gba` | B A, slanted | L, R | Start, Select |
| `gbc`, `gb` | B A, slanted | — | Start, Select |

Which standard button each label presses is each emulator's default for a standard gamepad (e.g.
BlastEm's `bindings.pads`), checked against the emulator during implementation, so no emulator is
reconfigured. That table lives beside the layouts, tested.

### Placement

- **Portrait: the pad takes the bottom half.** The game sits in the top half, scaled to fit at its
  aspect ratio. In the pad's half: d-pad left, buttons right, Start / Select centred between
  them, shoulders along the top edge of the half (left and right).
- **Landscape: the pad sits on the sides.** The game is centred at its aspect ratio; the d-pad (L
  above it) on the left, the buttons (R above them) on the right, Start / Select at the bottom of
  each side. When the sides are narrower than the controls need (a 4:3 tablet whose game fills
  the width), the controls overlay the edges of the game, translucent.
- **Pause** stays top right, inside the safe area, in both orientations.
- The pad publishes the rectangle the game may use (`pad.gameArea`, replacing `insets`), and
  updates it on rotate and resize; the host fits the engine's target into it.

### Who does what — simpler than §3

- **The host creates the pad** from the catalog's `system` (decision 1: host — confirmed).
- **Visibility follows the shared input**: while the game has the controls
  (`input.suspended === true`) the pad shows; when a menu opens (`resume()`) it hides and the menu
  is tapped. `UiInput` gains `onSuspend(listener)` (additive) so the host can follow it.
- So **the engine apps do not change**: no `EngineApp.touchLayout`, no `EngineAppHost.touch`. The
  contract only gains `TOUCH_LAYOUTS`, `createTouchPad()`, `exposeAsGamepad()`,
  `UiInput.trigger()` / `onSuspend()`, and `'touch'` as a source.
- Engines read the pad through the Gamepad API bridge (decision 2 — confirmed by "inicialmente para
  los emuladores": all four emulators read gamepads through SDL or `getGamepads()`). Pause button
  (decision 3) — kept.

### Launcher work (play.germade, its own record when this lands)

Create the pad on emulator routes with the system's layout, `exposeAsGamepad()` before the engine
starts, compose it into `createInput({ gamepads })`, fit the engine's target to `pad.gameArea`,
and a settings entry for opacity and size. Verified on a real phone: each emulator's game moves
with the pad, in both orientations.

### Testing — additions

- Placement as a pure function of (viewport, safe areas, game aspect ratio, layout): portrait
  bottom half, landscape sides, the overlay fallback when the sides are too narrow; tested.
- The per-system label → standard button table against each emulator's defaults.
- `demo/touchpad.html` gains a system selector and an orientation toggle.

### What each emulator reads (checked against the sources, not assumed)

| system | emulator | buttons (standard index) | source |
| --- | --- | --- | --- |
| Mega Drive | BlastEm | A 0, B 1, C 5, X 2, Y 3, Z 4, Mode 8, Start 9 | `default.cfg` at the pinned rev `6d1a7447ee9e` (`bindings.pads.default`) |
| Neo Geo | FBNeo | A 0, B 1, C 2, D 3 ("fire N" = joystick button N-1); d-pad through the game controller | `gamc.cpp` `GamcPlayer`, `inp_sdl2.cpp` at the pinned rev |
| SNES | snes9x | B 0, A 1, Y 2, X 3, L 4, R 5 (by position) | `snes9x.sdk.ts` |
| GBA / GBC / GB | mGBA | A 0, B 1, L 4, R 5 | `mgba.sdk.ts` |

And the path the pad takes into an SDL engine (Emscripten `libhtml5.js`, SDL2
`SDL_sysjoystick.c` / `SDL_gamecontrollerdb.h`):
- SDL enumerates `navigator.getGamepads()` at start-up and listens for `gamepadconnected` on the
  window, reading `event.gamepad` — so the pad is exposed before the engine starts, and announced
  with a plain `Event` carrying `gamepad`.
- SDL re-reads a pad only when its `timestamp` moved (or is 0) — the pad moves it on every change.
- SDL2's Emscripten build has a `default` mapping, "Standard Gamepad" (a b0, b b1, x b2, y b3,
  shoulders b4/b5, back b8, start b9, d-pad b12–15), so any standard pad is a game controller —
  BlastEm's `rightshoulder → C` and `leftshoulder → Z` land where the layout says.
- snes9x and mGBA read **only index 0**: the pad takes the first index no physical pad holds.

### What was added (`src/engine-specs.ts`, still one file, no dependencies)

- **`UiInput`**: `trigger(action, detail?)` (default source `'touch'`; while suspended only
  `menu` passes), `onSuspend(listener)` (changes only), and `'touch'` in `UiActionDetail.source`.
- **`TOUCH_LAYOUTS`** — `megadrive` (6 buttons), `neogeo` (A–D in the AES's rising row, its
  colours), `snes` (diamond, Super Famicom colours, L R), `gba` (B A, L R), `gbc`, `gb`. Each
  carries the game's aspect ratio for placement.
- **`placeTouchPad(layout, viewport, { scale, minGameScale })`** — pure geometry. Portrait: the
  bottom half (shoulders and pause along its top, d-pad left, buttons right, Select / Start along
  its bottom), the game the top half. Landscape: the sides; the game shrinks to make room down to
  70 % of the screen's height, below that it keeps the screen and the controls overlay its edges
  (`overlay: true`, more transparent). Safe areas respected; every target ≥ 48 px.
- **`createTouchPadCore()`** — fingers → standard buttons, pure: a finger keeps what it landed on
  (d-pad: eight 45° sectors and a dead zone; buttons: slide freely, the gap between neighbours
  presses both; keys: let go by sliding off); where the d-pad's and the buttons' margins meet on a
  narrow phone, the nearer one (by its own size) takes the finger; presses shorter than 50 ms are
  latched; `releaseAll()` and a new placement drop everything at once.
- **`touchDpadAt()`, `touchFacesAt()`** — the hit tests, exported for hosts that draw their own.
- **`createTouchPad(target, options)`** — the DOM: Pointer Events with capture on the pad's
  zones, `touch-action: none`, no selection / callout / context menu; released on blur and on a
  hidden page; `navigator.vibrate(8)` on press where it exists; `mode: 'auto'` (shows from the
  first touch on a coarse pointer, gone on a key or a physical pad) or `'always'`; `opacity`,
  `scale`; `gameArea` + `onLayout()` for the host to fit the game; re-placed on resize / rotation.
- **`exposeAsGamepad(pad)`** — wraps `navigator.getGamepads()`, first free index, announces,
  moves if a physical pad takes its index, `release()` restores everything.
- **`connectTouchPad(pad, input)`** — shown while the input is suspended (game), hidden in menus,
  the pause button → `input.trigger('menu')`.

Deviation from the extension, on purpose: in **portrait the pause button sits at the top centre of
the pad's half**, between the shoulders, not top right — top right of the screen is the game's
picture, and top right of the half is R's place. Landscape: top right, as planned.
