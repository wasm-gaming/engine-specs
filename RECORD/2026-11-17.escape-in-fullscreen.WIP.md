# Escape in fullscreen opens the pause menu

## 2026-11-17 15:45 UTC — Report and plan

Report from the owner (play.germade): in fullscreen, Escape leaves fullscreen instead of opening
the pause menu.

Cause: the browser keeps Escape for leaving fullscreen; the page never gets that keydown, so
`createInput()` never fires `menu`.

Plan, all in `createFullscreenToggle()` (every engine app uses it; nothing changes in the apps):

1. **Keyboard Lock** (Chromium: Chrome, Edge, Opera): when the root enters fullscreen,
   `navigator.keyboard.lock(['Escape'])`; on leaving, `unlock()`. Escape then reaches the page
   (→ `menu` in game, `back` in menus), and the player leaves fullscreen by **holding** Escape (the
   browser says so on screen), with Alt+Enter / Cmd+Enter, Select + Y, or the pause menu's entry.
2. **Without Keyboard Lock** (Firefox, Safari) or if `lock()` is refused: when fullscreen ends and
   the toggle did not ask for it, the Escape the browser took is given back — a `keydown` Escape
   dispatched on the toggle's `target` (the window), so `createInput()` hears what the player
   pressed: `menu` in game (the pause menu opens), `back` in a menu. Not done while the lock was
   held (the Escape already arrived).
3. Options for tests and hosts: `keyboard` (the Keyboard Lock object; default
   `navigator.keyboard`), `giveBackEscape` (default `true`).
4. UX.md, Fullscreen section: the two behaviours.
5. Tests: lock on enter / unlock on leave; Escape given back on a browser exit without lock; not on
   our own toggle; not while locked.
6. Release (patch, 0.6.2 by the workflow). Then each engine that uses the toggle bumps
   `@wasm-gaming/engine-specs` to 0.6.2 (its build copies the runtime next to the SDK) and
   releases: BlastEm, jgenesis, snes9x, mGBA, FBNeo, RSDKv3, RSDKv4, RSDKv5, Sonic 3 A.I.R. Then
   play.germade bumps their pins.

## 2026-11-17 16:05 UTC — Walkthrough and checks

Adds: what was built (as planned) and the checks.

- `src/engine-specs.ts`, `createFullscreenToggle()`:
  - options `keyboard` (`KeyboardLockLike`, default `navigator.keyboard`) and `giveBackEscape`
    (default `true`);
  - on entering fullscreen, `lock(['Escape'])` (kept only if still fullscreen when granted); on
    leaving, `unlock()`; `destroy()` unlocks too;
  - on leaving without the toggle asking and without the lock: a `keydown` Escape (a
    `KeyboardEvent` where there is one) dispatched on `target`.
- `UX.md`, Fullscreen: Escape keeps opening the pause menu; holding it leaves (Chromium).
- `tests/settings.test.mjs`: one test — lock / unlock with no Escape dispatched, give-back on a
  browser exit without lock, none on our own toggle, the same when `lock()` is refused, opt-out.
- `make test`: 94 / 94.
- Chromium, BlastEm 0.3.0's app in play.germade with this runtime copied in:
  - Alt+Enter → fullscreen; Escape → pause menu, still fullscreen; Escape → game.
  - With `navigator.keyboard` removed (as Firefox / Safari): the browser leaving fullscreen
    (`document.exitFullscreen()` from outside the toggle) → the pause menu opens. With the
    published runtime the game kept running.
  - Not reproducible headless: Playwright's Escape is not the browser's own, so the browser does
    not leave fullscreen on it with either runtime. To check on a real browser.

Suggested commit: `feat: Escape opens the pause menu in fullscreen (Keyboard Lock, or given back)`

## 2026-11-17 16:40 UTC — The keys bound to the pad's buttons work in menus

Adds: a second report for the same release, and its plan.

Report: in a pause menu the hints say "A" and "B" (the pad), and the owner, on a keyboard, pressed
the keys bound to the game's A and B (BlastEm: A and S). Nothing happens: menus take Enter / Space
and Escape / Backspace only. The owner wants those keys to work as the pad buttons they stand
for, and the hints to show which key each pad button is.

Plan (engine-specs):
- `menuKeyAliases(bindings, { keymap, padmap })`: from an app's control bindings
  (`{ code, button }` per game button), the keys of the buttons the menus use, as
  `{ [code]: action }` through `UI_PADMAP` (A accept, B back, X / Y more, LB / RB prev / next,
  Start menu, the d-pad). A key the menus already use (`UI_KEYMAP`: Enter, Space, Escape, Q, E, V,
  arrows…) keeps its meaning and is left out, so it never means two things.
- `UiInput.setKeyAliases(aliases)` (optional on the type, as `mute`): `createInput()` hears them by
  `KeyboardEvent.code`, after its own keymap, with the same rules (not while suspended, muted or
  typing in a field).
- `menuKeyHint(aliases, button)`: the key label a hint shows next to a pad button (`'S'` for B in
  BlastEm), or `''`.
- Tests for the three.

Then, in each engine app (with the engine-specs bump already planned): call
`host.input.setKeyAliases?.(menuKeyAliases(bindings))` at mount and when the controls change, and
render hints as the pad button plus its key. play.germade bumps engine-specs too, since the input
is the launcher's (`host.input`); with an older launcher the aliases are simply not there.

### Walkthrough (2026-11-17 17:00 UTC) — key aliases

- `UiInput.setKeyAliases()` (optional on the type) and `createInput()`'s implementation: aliases by
  `code`, after the keymap, same rules (suspended, muted, editable).
- `menuKeyAliases(controls)` and `menuKeyHint(controls, button)`, with a private `keyOfCode()` to
  leave out the keys the keymap already uses.
- UX.md: the paragraph under the actions table.
- `tests/settings.test.mjs`: 3 new tests (aliases from BlastEm's layout, hints, input behaviour).
  `make test` 97 / 97.

Suggested commit: `feat: the keys bound to the pad's buttons work in menus (setKeyAliases, menuKeyAliases, menuKeyHint)`
