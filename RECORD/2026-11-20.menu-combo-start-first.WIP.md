# Select + Start opens the menu only when Select is pressed first

**Status: Plan — awaiting approval before any code changes.**

Related: the in-game half of the same report (the pad never reaches the RSDK engines) is in
rsdkv3/4/5-wasm, `RECORD/2026-11-20.gamepad-lost-at-sdl-init.WIP.md`.

## 2026-11-20 11:20 UTC — Report and diagnosis

Report from the owner (play.germade.dev, Sonic 1, DualSense / GuliKit X, standard mapping):
Escape opens the pause menu, Select + Start does not.

Reproduced in headless Chromium on the live site with a fake standard pad, in game (input
suspended):
- Select held, then Start → pause opens.
- **Start held, then Select → nothing.**

Cause, in `createInput()`'s `poll()`: plain Start (button 9) is `menu` in `UI_PADMAP`. Pressed
alone while suspended it is not fired, but it still enters `held` as `menu`. When Select joins,
`pressed()` reports `menu` again (now as the combo) — and since `menu` is already held, no
transition, nothing fires. Starting with Start is the natural order for many players.

## Plan

`src/engine-specs.ts`, `createInput()`:
- Track the combo on its own: per pad slot, whether Select + Start was down last poll. The combo
  fires `menu` on its own rising edge, whatever `held` says about plain Start, and is the only
  `menu` that gets through while suspended (unchanged rule).
- Resumed (in a menu), plain Start then Select must not fire `menu` twice: a combo edge while
  `menu` was just delivered by plain Start in the same press is swallowed.
- Tests (`tests/`, fake pads + manual `poll()`): Start→Select and Select→Start both fire one
  `menu` while suspended; one `menu` when resumed; plain Start suspended fires nothing; holding
  the combo does not repeat.
- Release as a patch (0.6.3). The engines copy the runtime at build and the launcher bundles its
  own copy: each picks it up with its next dependency bump (play.germade's bundle included).

## 2026-11-20 11:40 UTC — Walkthrough (approved: "adelante, aplica los dos planes")

- `src/engine-specs.ts`, `createInput()`: a per-slot `comboMenu` set remembers which pads held
  Select + Start on the last poll; `poll()` computes the combo's rising edge (`comboEdge`). When
  `menu` is already held (plain Start first) and the combo edge arrives while suspended, `menu`
  fires once. Resumed, plain Start has already delivered it, so nothing more. Cleared on `destroy()`.
- `tests/ui.test.mjs`, three new tests: both orders fire one `menu` in game (no repeat while held,
  nothing when Select is let go); Start then Select in a menu is one `menu`; the combo on a second
  pad while the first holds Start. The first and third fail without the fix, pass with it.
- `make test`: 100 / 100.

Not probed: jgenesis (needs WebGPU, not in headless Chromium; it turns the pad into synthetic

So the combo fix is the one change every engine needs; it reaches them through this release.
